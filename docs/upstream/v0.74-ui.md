## 1. Chat rendering performance (MERGE)

### `77b6c38b` — perf(chat): only render the chat lines that fit on screen
Only passes visible items to list.SetItems. Large sessions no longer
render thousands of blocks that can't be seen.

**Files changed:** `internal/ui/model/chat.go` — the render path
**Check:** Our `Chat.Draw` or `Chat.View` — does it build items for the
whole session? If yes, filter to visible range. The Viewport has
`VisibleLineCount`/`Offset` that we should check against the item list.

---

### `6b101f38` — perf(chat): skip re-rendering chat list items that have not changed
Implements identity hash on each block; rebuildMdBlocks only re-renders
blocks with different hash. Cuts Glamour calls by orders of magnitude.

**Files changed:** `internal/ui/chat/md_block.go`, `internal/ui/model/mdview.go`
**Check:** Our `rebuildMdBlocks()` in `mdview.go` — does it re-render all
blocks every call? If yes, add hash caching (we already have `Block.ID` —
use it as identity key).

---

### `771117ca` — perf(chat): cache prefixed render of chat messages
Prefix rendering (user lambda, focused bar) cached per block so focus
toggle doesn't re-Glamour.

**Files changed:** `internal/ui/chat/md_block.go` — `MdBlockItem.Render()`
**Check:** Our `MdBlockItem.Render()` — prefix is cheap but the Glamour
portion is expensive. Cache full rendered output, invalidate on content
change.

---

### `65f30a13` — perf(chat): skip re-parsing the rendered chat when nothing has changed
Check if any event actually changed the chat content before running
SplitBlocks → rebuildMdBlocks.

**Files changed:** `internal/ui/model/mdview.go`
**Check:** Our `MdAppendedMsg`/`MdTruncatedMsg` handlers — do they always
re-parse? Add dirty flag.

---

### `6938dedd` — perf: batch streaming message updates
Group rapid streaming updates into one save+notification per short window
instead of per-token. Finishes, tool calls, and errors go through immediately.

**Files changed:** `internal/agent/agent_run.go` — Save/notification path
**Check:** Our streaming update: when LLM streams tokens, does each token
trigger a DB save + UI notification? If yes, batch them with a
~100ms debounce or interval timer.
