✅ **MERGED** (PR #119)

Replace Go's default unlimited connection pool with `SetMaxOpenConns(1)`.

### `40108413` — fix(db): prevent SQLITE_NOTADB corruption under concurrent sub-agents
✅ **MERGED** (PR #119)

Two changes:
1. `db.SetMaxOpenConns(1)` — concurrent sub-agents serialize through one
   SQLite handle, eliminating cross-handle WAL/checkpoint races.
2. Add `_txlock=immediate` to DSN — `BEGIN IMMEDIATE` acquires
   reserved-writer lock upfront. Concurrent writers queue cleanly on
   `busy_timeout` instead of racing deferred-to-writer upgrade.

For the ncruces driver the DSN must use `file:` URI prefix for query
params to be parsed; the plain path form silently ignores `_txlock`.

**Files changed:** `internal/db/db.go` (Open call DSN)
**Check:** What SQLite driver are we using? (`modernc.org/sqlite` or
`ncruces/go-sqlite3`) — affects DSN format for `_txlock`.

## Data directory lock (MERGE with rename)

### `6923820a` — feat(db): refuse to open a data directory in use by another crush
❌ **SKIPPED** (PR #119) — flock adds complexity without real protection

### `3c981c19` — chore(db): log lock metadata write failures
❌ **SKIPPED** (PR #119) — companion to `6923820a`

**Why both were skipped:** Upstream `6923820a` used `LOCK_EX` (exclusive)
to prevent a second process from opening the data directory at all. That
is the correct design for a client-server model where one long-lived
process owns the database.

Lenos runs multiple short-lived CLI processes sharing the same
`lenos.db` — `lenos session show` and `lenos stats` from different
terminals, or concurrent sub-agents spawned by an orchestrator. An
exclusive process-level lock would block all of these, breaking a hard
requirement.

For normal operation, SQLite WAL mode with `_txlock=immediate` and
`busy_timeout=30000` handles cross-process write serialization correctly
without external locking. The remaining gap (concurrent goose.Up
migration races) is documented as a known limitation below; fixing it
requires a migration-specific mechanism, not a process-wide exclusive
flock.

## Known limitation: concurrent migrations are unsafe

`goose.Up()` in `internal/db/connect.go:65` uses the legacy goose API
without a provider-level lock. While `gooseMu` serializes within a single
process, two lenos processes can both read the old DB version and race
through `goose.Up()`. `_txlock=immediate` serializes individual write
transactions but not the whole "read version → choose migrations →
apply" sequence.

Goose v3's `Provider.Up()` supports table-based locking (`goose_lock`)
via `WithLocker()`, but `goose.Up()` (the legacy function we use) does
not enable it. Fixing this requires switching to the Provider API with
an explicit locker — or a migration-only cross-process lock. Neither is
planned short-term; migration races are unlikely in practice because
lenos releases do not ship frequent schema changes.
